# ドメイン分析: 非同期TRPG風ゲーム「遺跡漁りとドブさらい」

**Date**: 2025-10-06
**Phase**: Domain-Driven Design Analysis
**Status**: Complete

## 概要
Domain-Driven Design (DDD) の観点から、プロジェクトの事業領域 (Business Domain) と業務領域 (Subdomain) を分析し、中核 (Core)、一般 (Generic)、補完 (Supporting) の3つのカテゴリーに分類する。

---

## 事業領域 (Business Domain)

**ドメイン名**: 非同期TRPGゲームプラットフォーム

**事業目的**: 忙しいユーザーが、自分のペースで物語を楽しめる非同期なTRPG体験を提供すること。

**中核的な価値提供**:
- 時間・場所の制約なく参加できるTRPG体験
- プレイヤー自身が物語を紡ぐインタラクティブな体験
- シナリオ作成者・GM・プレイヤーの三者が協調するエコシステム

---

## 業務領域 (Subdomain) の分類

### 1. 中核業務領域 (Core Subdomain)

これらは、プロジェクトの競争優位性を生み出す、**他では代替できない独自のビジネスロジック**を含む業務領域。

#### 1.1 **ゲームセッション管理**
- **責務**: ゲームプレイ全体のライフサイクル管理、非同期進行制御
- **集約**: `GameSession` (主要集約ルート)
- **重要な理由**:
  - 非同期TRPGの中核体験を提供
  - 複雑なゲーム状態の一貫性保証
  - プレイヤー間の協調を調整
- **独自性**:
  - 非同期プレイに特化した状態管理
  - イベント駆動による巻き戻し・再生機能
  - 動的なシーン遷移とイベント発火制御

#### 1.2 **シナリオ設計システム**
- **責務**: 再利用可能なシナリオ構造の定義、派生シナリオ作成
- **集約**: `ScenarioTemplate` (二次集約ルート)
- **重要な理由**:
  - プラットフォームのコンテンツ基盤
  - シナリオ作成者のクリエイティビティを実現
  - 動的イベントシステムによる柔軟な物語構造
- **独自性**:
  - シーン・イベント・トリガーの階層構造
  - 条件分岐・ループを含む複雑なシナリオフロー
  - ビジュアルエディター統合によるグラフベース設計

#### 1.3 **カード・タグシステム**
- **責務**: ゲーム進行の核となるカード使用・所持判定、キャラクター状態管理
- **エンティティ**: `Card`, `Tag`
- **重要な理由**:
  - TRPGのアクション表現の中核
  - キャラクター成長・物語進行の駆動要素
  - 独自のゲームメカニクスを実現
- **独自性**:
  - カード使用による動的イベント発火
  - タグによる状態管理・条件分岐
  - 選択肢カードの排他制御

---

### 2. 補完業務領域 (Supporting Subdomain)

これらは、中核業務を支援するが、**プロジェクト固有の要件に特化したカスタムロジック**を含む業務領域。既製ソリューションでは対応困難。

#### 2.1 **キャラクター管理**
- **責務**: プレイヤーのキャラクター作成・管理、セッション間の永続化
- **集約**: `Character` (二次集約ルート)
- **重要な理由**:
  - プレイヤーの長期的な資産管理
  - セッション間でのキャラクター成長
  - シナリオ参加制限の管理
- **カスタム性**:
  - セッション専用キャラクターコピー
  - シナリオ再参加制限ロジック
  - 持ち込みカード vs 配布カードの区別

#### 2.2 **ダイスロールシステム**
- **責務**: 2d6基本のダイス判定、有利/不利システム、判定条件評価
- **エンティティ**: `DiceNotation`, `DiceResult`
- **重要な理由**:
  - TRPGの確率的判定メカニクス
  - 公平性・再現性の保証
  - パーティ判定などの複雑な条件
- **カスタム性**:
  - 有利/不利システムの修正値計算
  - パーティ判定 (全員成功 or 誰か1人成功)
  - WebAssemblyによる高速確率計算

#### 2.3 **イベントログシステム**
- **責務**: 全プレイヤーアクション・ロールプレイの記録、非同期閲覧
- **エンティティ**: `EventLog`, `LogEntry`
- **重要な理由**:
  - 非同期プレイの進捗把握
  - 巻き戻し・再生機能の基盤
  - 物語体験の記録
- **カスタム性**:
  - 可視性制御 (全員/GM/個人/パーティ)
  - イベントタイプ別フィルタリング
  - Event Sourcing統合

---

### 3. 一般業務領域 (Generic Subdomain)

これらは、**既製ソリューション・ライブラリで代替可能**な業務領域。独自実装よりも、既存技術の統合が推奨される。

#### 3.1 **ユーザー認証・識別**
- **責務**: ユーザーID管理、簡素な識別機能
- **既製ソリューション**: 将来的にID/パスワード認証、JWT、OAuth等
- **現状**: 初期実装ではログイン不要（簡素化）
- **代替可能性**:
  - Auth0, Firebase Authentication等のSaaSで代替可能
  - 認証ロジック自体は汎用的

#### 3.2 **データ永続化**
- **責務**: IndexedDB、将来的にPostgreSQL/Neo4jへのデータ保存
- **既製ソリューション**: idb, Drizzle ORM, Neo4j Driver
- **現状**: IndexedDBラッパー (`event-store.ts`, `session-store.ts`)
- **代替可能性**:
  - ORMライブラリで標準的なCRUD操作
  - Event Sourcing ライブラリ (Thalo等) で抽象化可能

#### 3.3 **クロスタブ同期**
- **責務**: BroadcastChannelによる複数タブ間の状態同期
- **既製ソリューション**: BroadcastChannel API (ブラウザ標準)
- **現状**: `event-store.ts` で実装済み
- **代替可能性**:
  - WebSocketライブラリ (Socket.io等) で代替可能
  - 汎用的な同期パターン

#### 3.4 **WebAssembly FFI統合**
- **責務**: Rust ↔ TypeScript間の型安全なメッセージング
- **既製ソリューション**: wasm-bindgen, tsify, ts-rs
- **現状**: `wasm_interface.rs`, `simple-worker-service.ts`
- **代替可能性**:
  - WebAssembly統合パターンは確立済み
  - ツールチェーンで自動化可能

#### 3.5 **UIコンポーネントライブラリ**
- **責務**: 再利用可能なReactコンポーネント (Button, Card, Modal等)
- **既製ソリューション**: Chakra UI, Material-UI, Radix UI等
- **現状**: カスタム実装 (`packages/ui`)
- **代替可能性**:
  - 既存UIライブラリで十分代替可能
  - Tailwind CSS + Headless UIの組み合わせ

## ドメイン境界の明確化

### オニオンアーキテクチャとの対応

```
Domain Layer (中核業務領域)
├── GameSession (集約ルート)
├── ScenarioTemplate (集約ルート)
├── Character (集約ルート)
├── Card, Tag (エンティティ)
└── RuleEngine, DiceSystem (ドメインサービス)

Application Layer (補完業務領域)
├── UseCases (セッション作成・進行・終了)
├── Commands (CreateSession, UseCard, RollDice)
└── Queries (GetSessionState, GetCharacterStats)

Infrastructure Layer (一般業務領域)
├── Persistence (IndexedDB, PostgreSQL, Neo4j)
├── WebAssembly FFI (wasm-bindgen統合)
├── BroadcastChannel (クロスタブ同期)
└── Authentication (将来実装)
```

## 戦略的設計判断

### 中核業務への投資優先度

**高優先度 (MVP必須)**:
1. **GameSession集約**: TDD必須、複雑なルール検証
2. **ScenarioTemplate集約**: ビジュアルエディター統合
3. **Card/Tagシステム**: イベント発火・条件分岐ロジック

**中優先度 (MVP後)**:
4. **Character集約**: カード・タグ管理機能拡張
5. **DiceRoll**: パーティ判定・複雑な修正値対応
6. **EventLog**: 高度フィルタリング・検索

**低優先度 (将来拡張)**:
7. **ユーザー認証**: 初期は簡素化、後でSaaS統合
8. **データ永続化**: IndexedDBから段階的にバックエンド移行

### 既製ソリューション採用方針

**採用推奨**:
- **認証**: Auth0, Firebase Authentication
- **データベース**: Drizzle ORM (PostgreSQL), Neo4j Driver
- **UI**: Tailwind CSS + Radix UI (将来)

**カスタム実装継続**:
- **ゲームロジック**: 独自性が高く、既製品では代替不可
- **シナリオエディター**: React Flowベース、カスタマイズ必要
- **Event Sourcing**: ゲーム固有のイベント構造

## 境界づけられたコンテキスト (Bounded Context)

### 1. ゲームプレイコンテキスト
- **境界**: GameSession, EventLog, DiceRoll
- **言語**: セッション、シーン、イベント、判定
- **責務**: 実際のゲーム進行管理

### 2. シナリオ設計コンテキスト
- **境界**: ScenarioTemplate, SceneDefinition, EventDefinition
- **言語**: シナリオ、シーン、トリガー、条件、効果
- **責務**: 再利用可能なシナリオ構造の定義

### 3. キャラクターコンテキスト
- **境界**: Character, Card, Tag
- **言語**: キャラクター、所持品、スキル、履歴
- **責務**: プレイヤー資産の長期管理

### 4. ユーザーコンテキスト (将来)
- **境界**: User, Authentication, Authorization
- **言語**: ユーザー、ログイン、権限
- **責務**: プラットフォームアクセス管理

## 依存関係の方向

```
┌─────────────────────────────────────────┐
│   中核業務領域 (Core Subdomain)         │
│   - GameSession                         │
│   - ScenarioTemplate                    │
│   - Card/Tag System                     │
└───────────────┬─────────────────────────┘
                │
                ↓ (依存)
┌─────────────────────────────────────────┐
│   補完業務領域 (Supporting Subdomain)   │
│   - Character                           │
│   - DiceRoll                            │
│   - EventLog                            │
└───────────────┬─────────────────────────┘
                │
                ↓ (依存)
┌─────────────────────────────────────────┐
│   一般業務領域 (Generic Subdomain)      │
│   - User Authentication                 │
│   - Data Persistence                    │
│   - Cross-Tab Sync                      │
│   - WASM FFI                            │
└─────────────────────────────────────────┘
```

**原則**:
- 中核領域は他の領域に依存しない (純粋性維持)
- 補完領域は中核領域の概念を使用可能
- 一般領域は全ての領域から利用可能

---

## まとめ

### 中核業務領域 (Core)
1. **ゲームセッション管理** (GameSession)
2. **シナリオ設計システム** (ScenarioTemplate)
3. **カード・タグシステム** (Card, Tag)

### 補完業務領域 (Supporting)
1. **キャラクター管理** (Character)
2. **ダイスロールシステム** (DiceRoll)
3. **イベントログシステム** (EventLog)

### 一般業務領域 (Generic)
1. **ユーザー認証・識別** (User, Authentication)
2. **データ永続化** (IndexedDB, PostgreSQL, Neo4j)
3. **クロスタブ同期** (BroadcastChannel)
4. **WebAssembly FFI統合** (wasm-bindgen)
5. **UIコンポーネントライブラリ** (packages/ui)

### 戦略的判断
- **中核領域への投資**: TDD必須、独自実装、最高品質
- **補完領域**: カスタム実装、中核に合わせた設計
- **一般領域**: 既製ソリューション優先、統合のみ

この分析により、開発リソースの優先順位付けと、将来的なリファクタリング判断の指針が明確になる。
