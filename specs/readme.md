# 非同期TRPG風ゲーム CarTaGraph 仕様書

このディレクトリは、プロジェクトの「唯一の信頼できる情報源 `Single Source of Truth` 」として、システムの意図・構造・振る舞い・仕様をすべて記録する。

# 読み方

本プロジェクトは「Specification-Driven Development（SDD）」の考え方に基づき、
仕様を最初に書き、そこから実装・テスト・リリースへ派生する構成になっている。

| 対象読者         | 仕様書の活用                                                 |
| ---------------- | ------------------------------------------------------------ |
| ステークホルダー | 全体像やストーリーを読むことで、システムの目的を理解         |
| 開発者           | ドメイン仕様や振る舞い仕様を通じて、実装時の意図を正確に把握 |
| テスター         | テスト仕様から、期待されるふるまいと検証観点を確認           |

# ディレクトリ構成

[[specs/readme]] # 本ドキュメント

## /concepts（理念・設計思想の層）

- 「なぜこの仕様が存在するのか」を説明する部分。
- ステークホルダーも開発者もここから入る。
- ドメインの意味づけ（目的論） を担う。

[[specs/concepts/vision]]
[[specs/concepts/domain]]

## /guides（体験と用語の層）

- 教科書的な導入部分。
- 実際のプレイヤーや作者の行動に沿って説明。
- Foamでリンクを多用して「物語的な導線」を作る。

## /references（形式仕様の層）

- ここがSDD的に最重要。
- すべての開発（Rust, TypeScript, テスト仕様）はここを唯一の参照元とする。
- WASM FFIやAPI定義、データモデルなどを Markdown で整備。
- 自動生成（将来的にOpenAPIやtsdoc化）も視野に入る。

## /personas（利用者視点の教科書）

- /guides の補足で、プレイヤー・作者それぞれの立場に沿った詳細解説。
- チーム内教育やドメイン理解共有に最適。

## /appendix（補助資料）

- 開発に直接関わらないが、仕様理解を助ける資料。
- 例：イベント一覧、コンテキストマップ、FAQ。

## /scrapbook (メモ・チラシの裏)

- まだ本仕様にはしないが浮かんだアイデアや下書きしたドキュメントを雑多においておく
